# 標案參謀室

個人自用的政府標案情報站。由兩個部分組成：

| 部分 | 檔案 | 作用 |
| :--- | :--- | :--- |
| 前端網頁 | `標案參謀室.html` | 單一檔案，所有頁面與邏輯都在裡面，資料存在瀏覽器 localStorage |
| 本機 proxy | `server.js` | ①把網頁服務出去 ②代為查詢政府電子採購網官網（瀏覽器有 CORS 限制，沒辦法直接爬） |

網頁本身純前端，理論上雙擊 `標案參謀室.html` 就能開，但「官網即時查」這一頁一定要 proxy
才會有資料，所以**建議一律從 proxy 開**（`http://localhost:5178/`），不要用 `file://`。

---

## 快速開始

需要 Node.js 20 以上。

**Windows**：雙擊 `start-windows.bat`。第一次會自動跑 `npm install`，之後直接啟動並開瀏覽器。

**macOS / Linux**：

```bash
./start-mac-linux.sh
```

或手動：

```bash
npm install     # 只需第一次
npm start
```

啟動後開 <http://localhost:5178/>。

想換連接埠：`PORT=8080 npm start`，同時到網頁的「設定 → 官網即時查 proxy」把位址改成一樣。

proxy 預設只綁 `127.0.0.1`，同一台機器以外連不進來。想從手機或區網另一台機器看，
啟動時加 `HOST=0.0.0.0`（自負風險，這支程式沒有任何身分驗證）。

```
│   ├── build-exe.mjs       打包成單一執行檔（Node SEA）
│   ├── exe-entry.mjs       打包後的入口（自動開瀏覽器、連接埠備援）

```

改版靠 git，不要再複製 `xxx.backup-日期.html` 放在資料夾裡（`.gitignore` 已經排除這種檔名）。
改壞了用 `git diff` / `git checkout -- src/` 還原。

```bash
npm install              # 第一次（裝 tailwindcss 等建置工具）
npm run build            # 改了 src/ 之後：重新產生 標案參謀室.html
npm test                 # 改完先跑這個（含「輸出檔是否落後 src」的檢查）
git log --oneline        # 看版本歷史
```

**改網頁要改 `src/`，不要直接改 `標案參謀室.html`。** 輸出檔第二行記著內容雜湊，
直接改過的話 `npm run build` 會停下來不覆蓋（確定不要那些修改才加 `--force`）。

**Tailwind 的 class 一定要寫完整**，不能用字串拼：`'bg-'+tone+'-100'` 建置時掃不到，
畫面會沒顏色。要寫成 `tone==='rose' ? 'bg-rose-100' : 'bg-slate-100'`。
`npm run build` 會點名可疑的拼接寫法。

## 打包成單一 exe 分享給沒裝 Node.js 的人

```
build\打包exe.bat        ← Windows 雙擊即可
npm run build:exe        ← 或用指令
```

產出 `dist/標案參謀室.exe`（約 86 MB，壓縮後約 32 MB）＋`使用說明.txt`。
同仁**不需要安裝任何東西**：雙擊 exe → 啟動本機伺服器 → 自動開瀏覽器。

用的是 **Node.js 官方的 SEA**（Single Executable Application），不是 pkg／nexe：

1. `esbuild` 把 `server.js` ＋ cheerio ＋ iconv-lite ＋ **HTML** 打成一支 CJS
   （SEA 的主程式只吃 CommonJS；HTML 用 `--loader:.html=text` 內嵌成字串）
2. `node --experimental-sea-config` 產生 blob
3. `postject` 把 blob 注入 `node.exe`

幾個必須知道的限制與設計：

- **blob 必須由跟目標 `node.exe` 相同版本的 node 產生。** 在 Windows 上打包時
  直接複製自己的 `node.exe`，最單純；在 Linux 上跨平台打包則會從 npm 抓
  `node-win-x64@<當前 node 版本>`（那個套件裡就是官方的 Windows node.exe）。
- **CJS 不支援 top-level await**，所以 `exe-entry.mjs` 把啟動流程包在 `main()` 裡。
- **bundler 會把 `import.meta.url` 變成空值**，`fileURLToPath` 會拋錯。
  `server.js` 因此用 `selfPath` 包了 try/catch，並據此判斷「是否為主程式」——
  被 import（含打包）時不會自己 `listen`。
- **版號要在編譯期固化**：`VERSION` 平常讀 `package.json`，但 exe 旁邊沒有那個檔，
  所以打包時用 `--define:__APP_VERSION__` 傳進去再 `setVersion()`。
  （`--define` 的值是 JS 運算式，字串只能包一層引號，包兩層會變成 `v"1.1.0"`。）
- **exe 旁邊放一份 `標案參謀室.html` 會覆蓋內建版本**，所以只改網頁時不必重新打包。
  黑色視窗會顯示讀到哪一份。
- 連接埠 5178 被占用時自動往上找到 5187（同仁可能不小心開兩次）。
  ⚠️ 不同連接埠在瀏覽器眼中是不同網站，**localStorage 資料是分開的**。
- 只綁 `127.0.0.1`，同網段的人連不進來。

### 分享時要先跟同仁講的事

- **Windows SmartScreen 會警告**（「Windows 已保護您的電腦」），要點「其他資訊 → 仍要執行」。
  因為沒有買數位簽章。
- 更麻煩的是：官方 `node.exe` 本身有簽章，注入 blob 之後**簽章會失效**
  （postject 會印 `The signature seems corrupted!`）。有些公司防毒對「未簽章又會開網路埠」
  的執行檔會直接隔離。我沒有動手移除那份失效簽章——手改 PE 標頭在無法實測 Windows 的
  情況下風險太高。若真的被隔離，退路是**資料夾版**：一份 `node.exe` ＋ `server.js` ＋
  `標案參謀室.html` ＋ 一個啟動用的 `.bat`，壓成 zip；沒有單一 exe 的隔離問題。
- 資料存在各人自己的瀏覽器裡，**換人換電腦就是空的**，要搬移請用頁尾的匯出／匯入備份。

## 兩條資料來源

這是理解整個網頁最重要的一件事：兩條來源涵蓋範圍不同，不會互相補齊。

| | 走 g0v / openfun API | 走本機 proxy 打官網 |
| :--- | :--- | :--- |
| 涵蓋 | 招標、決標、歷史案件、廠商 | **只有招標公告，且只有等標期內** |
| 即時性 | 落後官網數小時到一天 | 即時 |
| 用在哪些頁面 | 總覽、標案情報中心、機關洞察、市場與廠商、採購行事曆 | 官網即時查 |
| 設定位置 | 設定 → 標案資料 API | 設定 → 官網即時查 proxy |

### 機關只能「累積」，不能用名稱查

這支 API **沒有「用機關名稱查機關」的端點**。`searchbytitle` 只比對標案名稱，
不比對機關名稱（拿只出現在機關名的字串去查，回傳的每一筆標題都還是含該字串）。
所以機關名稱 → `unit_id` 沒辦法直接查，只能從已經抓下來的公告裡認識。

網頁因此維護一份**機關索引**（`pi_agency_index`，機關名 → `unit_id`）：
同步公告、標案查詢、廠商查詢、開標案詳情、進機關輪廓時都會自動收錄，
而且它**不隨公告快取的 21 天上限被裁掉**，所以用久了機關洞察的清單會越來越完整。

在機關洞察篩選不到想找的機關時，正確的繞路是：用那個名字到**標案情報中心**查標案，
開任一筆按「機關採購輪廓」——該機關就會進索引，之後就篩得到了。
空清單狀態的按鈕已經把這條路接好。

### API 設定

API 預設 `https://pcc-api.openfun.app`，備用 `https://pcc.g0v.ronny.tw`。
目前不帶 token 就能公開查詢，所以預設不送 `Authorization`
（`pcc-viewer` 公開設定檔裡那組 token 已被 API 端擋掉，網頁會自動忽略它）。
被限流的話到「設定 → API Token」填自己申請的。

## 八個頁面

| 頁面 | 做什麼 |
| :--- | :--- |
| **總覽** | 逐日同步全國公告存進瀏覽器（近 3／7／14 日，最多保留 21 天），加上追蹤中 14 日內截止的清單。機關洞察與行事曆都吃這份快取，所以第一次使用要先來這裡按「開始同步」 |
| **標案情報中心** | **四個固定欄位**（標案名稱／機關名稱／廠商名稱／統一編號）AND 搜尋，見下節；點進去看標案詳情（含投標門檻雷達），可加入追蹤或比較 |
| **官網即時查** | 走本機 proxy 直接問官網，只回等標期內的案子。可設關鍵字清單一次跑完（「關鍵字監控」），附 14 日內截止 |
| **機關洞察** | 從「已認識的機關」裡挑一個，向 API 抓它**全期間**公告（不受同步天數限制），看得標廠商排行＋**市場集中度**、**落標率**、**拒絕往來廠商**、**發包節奏**、採購輪廓，以及**機關對比**（見下面各節） |
| **市場與廠商** | 用廠商名稱或統編查它的得標紀錄、**對手常駐追蹤**、**廠商對比**；另有「已同步期間的得標廠商排行」（吃快取） |
| **採購行事曆** | 月曆呈現快取裡的公告量與追蹤案的投標截止日 |
| **追蹤清單** | 收藏的案子，可一鍵回頭向 API 更新截止日與預算 |
| **標案比較** | 最多 6 案並排。欄位可用預設組合（基本／投標門檻／金額與期限／全部）或自選，可只看有差異的列，另有算出來的欄位（剩餘天數、等標期、決標／預算比），可匯出 CSV |

標案詳情裡另有**投標門檻雷達**，見下面的專節。

## 發包節奏（機關洞察裡）

這是唯一一個「算」出來而不是「查」出來的功能，也不多打 API——它只用機關輪廓
已經抓下來的那份全期間公告清單。

**下次招標預估**：把標案名稱正規化成系列鍵（剝掉 `115年度`、`114~115年`、
`第2次` 這類會逐年變動的部分，但保留 `#1機` 這種識別用的編號），
同一系列的歷次招標公告排成時間軸，取**間隔中位數**推下一次。

兩個關鍵設計，都是被真實資料打過臉才長這樣的：

- **同一輪收攏**：距離上一次不到 240 天的招標視為同一輪（流標重招、分批、第2次公告），
  只留最早那一次。原本是「每曆年取最早一次」，但台電有個案子 2025/08/14 流標、
  2026/02/04 重招，跨了曆年所以兩筆都留下，174 天就被當成「半年一次的週期」。
- **只有像週期的才叫規律**：間隔接近 365／730／1095 天才標成年度／兩年／三年，
  其餘一律標**不規律**、淡化、排到後面，也不計入「120 日內招標」的統計。
  刻意**不設「半年」這一類**——單一個 150~250 天的間隔，光看數字無法跟流標重招區分，
  寧可標不規律，也不要給出看似精確的錯預測。

判讀時看兩個數字：**輪數**（只有 2 輪的預估很脆弱）和**慣例月份的命中比例**
（`3 月（5/5 次）` 比 `3 月（2/5 次）` 可信得多）。預估日已過又沒出現的系列，
可能已停辦、改名或併案。

以台電電力修護處（8,403 則公告）實測：173 個系列中 95 個規律
（年度 46、兩年 32、三年 17）、78 個不規律。

**流標與重招**：`無法決標公告` 之後，同系列還沒出現新招標公告的排在最前面——
機關通常會再來一次，也常伴隨放寬資格或調整預算。已重招的會顯示隔了幾天，
並算出這個機關流標到重招的中位天數。

限制：系列比對靠名稱正規化，**改名重招認不出來**；同一標案在不同機關代碼下
分別發包也會被當成兩個系列。

## 市場集中度、落標率、拒絕往來廠商

這三項都只是對已抓下來的公告再算一次，不多打 API。

**市場集中度**（在得標廠商排行上方）：以**件數**佔比算 CR1／CR3／CR5 與 HHI
（各家佔比百分比的平方和，0–10000），分級用競爭法常見門檻——
`<1500 分散`、`1500–2500 中度集中`、`>2500 高度集中`。
判斷「這個機關是不是被特定廠商把住、新進者有沒有機會」。
共同得標／複數決標的案子會同時計入每一家，所以件數總和大於案件數，集中度會被略微低估。
**只算真正得標的廠商**——公告的廠商名單同時列出得標與落標，詳見下面「廠商名單含落標廠商」。
（台電電力修護處實測：1,434 家、HHI 78、最大一家 6.5% → 分散。）

**落標率**（決標金額 ÷ 預算金額）：中位數、分佈、逐年趨勢、壓最低的 5 案。
只能算**同時有決標金額與預算金額**的案子，所以樣本數與涵蓋率一律顯示在旁邊——
低涵蓋率的中位數只代表「你已補齊金額的那些案子」，不是機關全貌。
比值 >3 或非正數會剔除（多半是複數決標總額對上單項預算）。
金額要按「補齊決標金額」逐案抓才有。

**拒絕往來廠商**（停權名單）：`拒絕往來廠商名單公告` 是獨立的公告類型，
所以這份名單本來就在抓下來的資料裡。用來查對手或潛在協力廠商有沒有被停權。
另外會**交叉比對**：被停權的廠商裡哪些同時也在本機關的得標名單上。
同一案同一天可能有多則（一家廠商一則）；有「更正公告」時這裡不會自動抵銷，
要確認目前狀態請到政府電子採購網的「拒絕往來廠商」專區。

## 四欄位 AND 搜尋

標案情報中心有四個固定欄位，**填幾個就要同時成立**：

| 欄位 | 能不能當主查詢 | 對應端點 | 每頁 |
| :--- | :--- | :--- | :--- |
| 統一編號 | ✅ 選擇性最高 | `searchbycompanyid` | 100 |
| 廠商名稱 | ✅ | `searchbycompanyname` | 100 |
| 標案名稱 | ✅ | `searchbytitle` | 50 |
| 機關名稱 | ❌ **API 沒有機關查詢端點** | — | — |

API 一次只能用**一個**條件查，所以程式會挑選擇性最高的當「主查詢」丟給 API，
其餘條件在前端篩。優先序：

**機關索引唯一命中 › 統一編號 › 廠商名稱 › 標案名稱**

只填一個條件時走原本的伺服器分頁；填兩個以上就進掃描模式（分批抓、可續掃）。
畫面上一定會標明主查詢是哪個欄位、掃了多少筆、前端又篩掉多少。

被主查詢用掉的那個欄位**不會再在前端複篩**——伺服器已經比對過，
再篩一次可能因為我的比對比伺服器更嚴而誤刪正確結果。

機關名稱是唯一不能當主查詢的欄位（實測多傳 `unit_name` 參數會被完全忽略：
總筆數不變、無關機關照樣回來），所以它有兩條路，差距很大，程式會自動選：

| | 精準路徑 | 掃描路徑 |
| :--- | :--- | :--- |
| 何時使用 | 機關名稱在**機關索引裡唯一命中** | 機關字串沒命中或命中多個 |
| 資料來源 | `listbyunit`，**每頁 1000 筆** | `searchbytitle`，每頁 **50 筆** |
| 涵蓋 | 該機關的公告（受 15 頁／輪上限），對這個機關**接近完整** | 只涵蓋掃到的頁數 |
| 一輪 | 最多 15 頁 = 15,000 則 | 5 頁 = 約 250 筆 |

**為什麼差這麼多**：`統包` 這種關鍵字全國有 10,000 筆（被 API 截斷在 100 頁），
掃 5 頁只看得到 250 筆，台電的案子可能只撈到幾筆；而 `listbyunit` 一頁就 1000 筆，
把某個電廠的公告全抓下來再篩標案名稱，結果對該機關是完整的。

所以**想查得完整，先到機關洞察把那個機關點一次**——它會進機關索引（`pi_agency_index`），
之後這裡就會自動走精準路徑，而且其他三個條件全部變成前端篩選，涵蓋最好。
掃描路徑的畫面下方也會列出索引命中的機關供一鍵切換。

兩條路都會標明涵蓋範圍：精準路徑顯示「在 X 的 N 則公告／官方共 M 則（第 1–p / t 頁）」，
掃描路徑顯示「已掃第 1–p 頁（約 N 筆），其中機關含『…』的有 M 筆」，都附續抓／續掃按鈕。

只填機關名稱時：唯一命中就直接列出該機關的公告；沒命中則說明 API 查不了，並指引去機關洞察。

四個欄位可以任意組合，例如：

- `標案名稱=統包` + `機關名稱=台灣電力` → 台電系統的統包案
- `廠商名稱=中興工程顧問` + `機關名稱=台灣電力` → 這個對手在台電得標了什麼
- `統一編號=…` + `標案名稱=監造` + `機關名稱=中油` → 某家廠商在中油的監造案

另有「清空條件」鍵，四個欄位都綁了 Enter。

## 投標門檻雷達（標案詳情裡）

招標公告的 detail 有 85 個欄位，真正決定「這案能不能投、要不要投」的只有十幾個。
門檻雷達把它們抽出來分四組（案件性質／競爭條件／資格與保證金／履約條件），
並把**客觀上多一道要求或風險**的項目標成琥珀色、彙總列在最上面：

| 條件 | 標記 |
| :--- | :--- |
| 是否屬統包 = 是 | 統包，需設計與施工整合 |
| 需技師簽證 = 是 | 須依技師簽證規則辦理 |
| 是否特殊採購 = 是 | 特殊採購，資格門檻較高 |
| 決標方式含「最低標」 | 以價格競爭為主 |
| 是否訂有底價 = 否 | 未訂底價 |
| 適用 GPA = 是 | 外商可參與，競爭範圍擴大 |
| 押標金額度有值 | 須繳押標金 |
| 須繳履約保證金 = 是 | 須繳履約保證金 |

標記只針對「客觀上多一道要求」的情況，**不替你判斷該不該投**。
沒有任何標記時會明說「沒有額外門檻」，避免空白被誤讀成資料沒抓到。

## 對手常駐追蹤與廠商對比

`searchbycompanyname` **每頁 100 筆**（中興工程顧問實測 4,681 筆、47 頁；
泰興工程顧問 553 筆、6 頁），所以不可能抓全歷史。這裡每家抓 `RIVAL_PAGES = 3` 頁（300 筆），
目的是看**最近在幹什麼**而非全歷史統計——畫面上所有數字都標明是抓取範圍內的，
並單獨顯示「官方總筆數」讓你知道抓到的只是一小部分。

每家對手會算出：**得標件數**與**落標件數**（都排除更正決標與定期彙送，否則會重複計入）、
主要機關、**共同得標夥伴**、**常同場競標對手**、最近 8 筆得標。

「夥伴」與「對手」是兩件不同的事，以前被混成一項：

| | 定義 | 怎麼判斷 |
| :--- | :--- | :--- |
| 共同得標夥伴 | 同一案**和它一起得標**的別家 | 雙方都在該案的得標名單裡 |
| 常同場競標對手 | 同一案出現、但**不是一起得標**的別家 | 至少一方落標 |

名單裡會出現廠商自己（有時同時有帶英文後綴與不帶的兩種寫法），
`sameVendor()` 會把這些認成同一家並排除。

**廠商對比**用同一份快照（最多 20 份），勾 2–4 家並排比 14 個指標，
外加一列「共同機關」——這幾家在抓取範圍內都有得標的機關。
抓取筆數不同的兩家不能直接比件數，比例類與名單類才有意義。

### 廠商名單含落標廠商

`brief.companies.names` 是該案**所有出現過的廠商**，得標與落標混在一起，
以前整份被當成得標名單用。實測 2026-09-01 全日 624 則決標公告：
1,169 個名字裡只有 **725 家真的得標**、417 家落標，得標件數因此**虛增 61%**。

分辨的方法在同一份 `brief.companies` 裡的 `name_key`，
它記錄每個名字是從詳細資料哪些欄位抓來的，**不必多打任何一次 API**：

| `name_key` 的欄位 | 意義 |
| :--- | :--- |
| `決標品項:第N品項:得標廠商N:得標廠商` | 得標 |
| `決標品項:第N品項:得標廠商N(共同投標廠商):得標廠商` | 共同投標且得標 |
| `決標品項:第N品項:未得標廠商N:未得標廠商` | 未得標 |
| `投標廠商:投標廠商N:廠商名稱` | 只知道有投標 |
| `標案內容:廠商名稱` | 拒絕往來公告的當事廠商（**沒有得標欄位**） |
| `英文公告:廠商名稱` | 同一家的英文名，不是另一家公司 |

一律走 `splitCompanies()` → `recVendors()`（得標，統計用）／
`recBidders()`（全部，顯示與拒絕往來比對用）。
多品項的案子同一家可能一項得標、另一項落標（實測有），**只要有一個純得標欄位就算得標**。

## 機關對比

機關輪廓要抓幾萬則公告才算得出來，不可能為了對比而同時抓兩三個機關。
所以**每次看完一個機關就自動存一份指標快照**（只存算好的數字，不存原始公告，最多 40 個），
之後在機關洞察頁勾 2–4 個就能並排比 17 個指標：資料涵蓋、流標率、廠商家數、
CR1／CR3／HHI、落標率中位數、規律發包系列、120 日內預估招標、拒絕往來則數、前三大廠商等。

每列會標出最高的一格——流標率、集中度這類「越高對新進者越不利」的用紅色，其餘用綠色。
若各機關的**資料涵蓋率差距超過 25%**，表格上方會警告：件數類指標會被資料量牽著走，
只有比例類（流標率、集中度、落標率）勉強可比。

快照**不會自動更新**，機關有新公告要再點一次那個機關才會刷新。

## 事件屬性傳字串的陷阱（改程式前務必看）

把字串當參數塞進 `onclick` / `onchange` 時**一定要用 `jsArg()`**，不可以直接
`JSON.stringify()`。屬性是用雙引號包的，而 `JSON.stringify` 產生的字串**也帶雙引號**：

```
onchange="toggleVsnapSel("亞新工程顧問",this.checked)"
                         ↑ HTML 解析器在這裡就把屬性結束掉
```

handler 變成語法錯誤，**按鈕完全沒反應，主控台也不一定看得到錯誤**。
實際發生過：廠商對比與機關對比的核取方塊、快速加入對手、更新／移除、重試按鈕
一共 9 處全是死的，而且畫面看起來很正常（核取方塊視覺上會打勾，因為那是瀏覽器
的預設行為，跟 handler 無關）。

判斷是不是中招：**看畫面上的計數有沒有跟著動**。當時標題寫「目前有 4 份廠商快照。」
卻沒有「，已勾 N 家」，就代表程式眼中一個都沒勾到。

`test/frontend.test.mjs` 有一支**掃原始碼**的測試守著這個寫法，
而且我驗證過「把 bug 放回去測試會失敗」——防護測試要能失敗才有價值。

另一個相關的坑：**勾選會重繪整個 `<details>`**，若只用 `sel.length>=2` 決定要不要加
`open`，使用者勾第一個時面板會當場收起來。所以重繪前要先讀目前的展開狀態沿用。

## 公告類型判斷的陷阱（改程式前務必看）

這個資料集的類型名稱大量共用子字串，隨手 `indexOf` 一定出錯。
以台電總公司 30,000 筆的實測分布為證：

| 誤判 | 後果 |
| :--- | :--- |
| `更正決標公告` 含 `決標公告` | 決標數、廠商件數、集中度、落標率全部**虛增 20.9%**（多 2,709 筆） |
| `無法決標公告` 含 `決標` | 「只看決標公告」會多列 **2,937 筆流標案** |
| `撤銷無法決標公告` 含 `無法決標` | 被當成流標，但語意相反 |
| `限制性招標(經公開評選…)公告` **不含** `招標公告` | **1,109 筆招標被漏掉** |
| `招標文件公開閱覽公告資料公告` 含 `招標` | 那是招標前的公開閱覽，不是招標本身 |

所以類型判斷全部集中在幾個函式，**不要在別處自己寫 `indexOf`**。
而且「統計」與「顯示」的定義不同，刻意分成兩組，不可互用：

| 用途 | 函式 | 定義 |
| :--- | :--- | :--- |
| 統計（一案一筆） | `isAward` / `isFailedAward` / `isTender` | 排除更正與撤銷 |
| 顯示（核取方塊） | `isAwardNotice` / `isTenderNotice` | **含更正**，因為更正公告也是該類別的資訊；但流標絕不混入決標 |

`isTender` 另有一份 `TYPE_NOT_TENDER` 排除名單（公開閱覽、徵求參考資料、財物變賣／出租、
公示送達、定期彙送、拒絕往來），因為這些名稱含「招標」或「公開取得」但不是招標本身。

## localStorage 配額（改程式前務必看）

全部資料都在 localStorage，而瀏覽器上限通常只有約 5 MB。公告快取是唯一會長到 MB 級的東西
（全國一天約 1,000 則，14 天就可能超過整個配額），所以配額處理**集中在 `LS.set()`**：

1. 直接寫，成功就結束
2. 失敗 → `reclaimDayCache()` 從公告快取丟掉最舊的日期騰空間 → 重試
3. 還是失敗 → `warnQuota()` 明確告知哪一筆沒存到（同一個鍵 30 秒內只提示一次，
   因為機關快照每次重繪都會寫）

**不要在別處直接 `localStorage.setItem`，也不要忽略 `LS.set` 的回傳值。**
使用者動作（加入追蹤、加入比較、加關鍵字、加對手）寫入失敗時會**把記憶體也回滾**，
否則畫面顯示「已追蹤」但重載就不見——那比直接報錯更糟。

其他相關設計：

- 公告快取用**筆數**上限（`DAYCACHE_MAX_RECORDS = 12000`）而不是天數。
  天數無法反映實際大小，而且原本的裁切迴圈有 off-by-one：
  條件是 `keys.length>3 && 寫入失敗`，裁到剩 3 天時 `3>3` 為 false 直接跳出，
  **那個「剩 3 天」的版本從來沒被寫進去**，記憶體已裁掉但 localStorage 還是舊值。
- 決標金額快取有上限（`AMOUNT_MAX = 8000`，LRU 淘汰）。它是逐案打 API 換來的
  （每筆約 0.32 秒），所以上限開大一點。
- 同步結束時**先寫機關索引再寫公告快取**——機關索引不可重建，不能被快取把配額吃光。
- 頁尾有**儲存用量條**，並區分「可重建快取」與「你的資料」；
  超過 70% 會提示。旁邊的**「只清快取」**只刪 `CACHE_KEYS` 裡的鍵，
  保留追蹤、比較、關鍵字、對手清單與機關索引——這是配額卡住時真正該按的按鈕。
  `test/frontend.test.mjs` 有測試守著 `CACHE_KEYS` 不可誤含使用者資料。

## 金額欄位的陷阱（改程式前務必看）

公告的金額欄位不能用 `pick()`（子字串比對）取，有兩個實測踩到的坑：

1. **「預算金額」旁邊有「預算金額是否公開」**，值是「是」／「否」。
   決標公告的鍵順序是 `已公告資料:預算金額是否公開` **排在** `已公告資料:預算金額` 之前，
   所以 `pick` 先撞到「是」，`parseMoney('是')` = 0。
   後果：落標率與比較頁的「決標／預算比」**永遠算不出來**，
   而且打開決標公告的標案詳情時「採購預算」會顯示「**是**」。
2. **「總決標金額」旁邊有 `總決標金額:remind`**（一段中文說明、無數字）與
   `投標廠商:投標廠商N:決標金額`（單一廠商金額，不是總額）。`pick` 會落到後者。

所以金額一律走 `pickMoney()`：先比對鍵的最後一段是否**完全相符**、跳過說明類欄位
（`是否`／`remind`／`說明`／`備註`／`理由`／`方式`／`條件`）、值必須能解析成正數；
決標公告沒有預算欄位時用 `pickMoneyAcross()` 回頭找招標公告。

決標金額快取帶 `v` 版本號（目前 `2`）。v1 的 `b`（預算金額）因為上述陷阱全部是 0，
所以版本不符的項目按「補齊決標金額」時會**重抓一次**。

## 機關公告抓取：分頁、限流與去重

`listbyunit` 每頁 1000 筆（約 630KB）。大機關很可觀——台電總公司 `3.13.31`
有 **40,243 則、41 頁**。三個實測踩到的坑：

1. **API 對訪客限流**（2026-10-07 查明）：閒置後可連打約 10 次，之後每 3 秒補 1 次額度，
   超過回 HTTP 429。**429 沒有 CORS 標頭**，所以瀏覽器只看到 `TypeError: Failed to fetch`——
   以前記成「連抓 15 頁就斷線」就是這個。現在所有請求都經過 `api()` 的共用節流
   （容量 8、每 3.2 秒補 1），撞到就等 6→12→20→30 秒再試，進度列會寫出在等什麼。
   每輪上限 30 頁（約 1.5 分鐘），可續抓。
2. **失敗不能丟掉已抓到的資料**。原本整個迴圈包在一個 try/catch 裡，第 16 頁一失敗，
   前面 15,000 筆全被丟掉，畫面只剩一句「載入失敗」。現在保留已取得的部分，
   並用橫幅講清楚抓到幾則、共幾頁，附「繼續往下抓」從斷點續抓。
3. **靜默截斷比報錯更糟**。沒抓完時，廠商排行、決標金額合計、發包節奏全都只涵蓋一部分。
   所以只要不完整，標題卡會顯示「已取得 X / 官方 Y」，發包節奏另有獨立警示
   （公告是新到舊排序，未抓完就等於**缺早年資料**，系列輪數會偏低、間隔可能算錯）。

另外會**濾除分頁重複**：抓第 N 頁與第 N+1 頁之間官網若新增公告，位移會讓邊界紀錄被重抓
（台電總公司 30,000 筆裡有 34 筆）。去重鍵是
`filename + job_number + date + type + 廠商名`——`filename` 單獨不是唯一鍵（會被多筆共用，
30,000 筆裡重複 1,026 次），`job_number + date + type` 也不是（同案同日可以有多則，
例如拒絕往來名單是一家廠商一則）。這個複合鍵實測與整筆 JSON 比對結果完全一致，但快 4 倍。
濾掉幾筆會顯示在標題卡上，數字才對得起來（電力修護處官方 8,405 − 重複 2 = 8,403）。

## proxy API

| 端點 | 說明 |
| :--- | :--- |
| `GET /api/health` | 健康檢查，網頁用它判斷 proxy 在不在。回 `version` `node` `cachedKeywords` `uptimeSeconds` |
| `GET /api/search?keyword=燃氣` | 單一關鍵字查詢，只回等標期內案件 |
| `GET /api/watch?keywords=燃氣,統包,監造` | 多關鍵字一次跑完、去重、附 14 日內截止清單。關鍵字上限 20 個 |

共同的篩選參數：

| 參數 | 說明 |
| :--- | :--- |
| `minBudget` | 預算下限 |
| `maxDays` | 幾日內截止 |
| `exclude` | 排除字詞，逗號分隔，比對案名與機關名 |
| `sort` | `deadline`（預設）或 `budget` |
| `pageSize` | 1–100，預設 100，只有 `/api/search` 吃 |

非數字的 `minBudget` / `maxDays` 視為未設定（不會靜靜地把結果篩成空的）。

回傳欄位：

```
caseId  name  orgName  tenderWay  tenderType
publishDate  deadline  remainingDays  tenderPeriod
publishISO  deadlineISO          ← 已解析成 ISO 字串，方便前端排序
budget  link
```

`/api/watch` 的每筆另外帶 `matched`（這筆是被哪些關鍵字命中）。

除了 `/api/*` 以外的路徑一律當同資料夾的靜態檔服務，根路徑 `/` 對應 `標案參謀室.html`。
`.git/`、`node_modules/`、`.env*` 與資料夾以外的路徑不會被服務出去。

| `pi_watch_keywords` | 關鍵字監控清單 |
| `pi_agency_index` | 機關索引（機關名 → `unit_id`），累積式，不會被裁掉 |
| `pi_agency_snap` / `pi_agency_snap_sel` | 機關指標快照（最多 40 個）與目前勾選對比的機關 |
| `pi_compare_view` | 標案比較的欄位組合、自選欄位、只看差異等顯示偏好 |
| `pi_agency_snap` / `pi_agency_snap_sel` | 機關指標快照（最多 40 個）與目前勾選對比的機關 |
| `pi_rivals` | 對手常駐追蹤清單（廠商名稱） |
| `pi_vendor_snap` / `pi_vendor_snap_sel` | 廠商指標快照（最多 20 份）與目前勾選對比的廠商 |

「可重建快取」＝ `pi_daycache`、`pi_amount_cache`、`pi_agency_snap(_sel)`、`pi_vendor_snap(_sel)`，
「你的資料」＝其餘全部。頁尾的「只清快取」只動前者。
| `pi_amount_cache` | 決標金額快取 |

頁尾的「匯出備份」帶走**追蹤、比較、關鍵字、機關索引、對手清單、比較欄位偏好**六項
（`version: 6` 的 JSON，匯入仍相容舊的 `version: 3`～`5`），
機關索引與對手清單是合併而非覆蓋。
公告快取、金額快取與各種快照不備份——重新同步或重新點一次就有。

**匯入會逐項確認真的寫進去**，任何一項失敗就明確列出是哪幾項，不會只顯示「備份已匯入」。
匯入是最容易撞到配額的時機（把備份還原到一台快取已滿的機器），而你可能已經把 JSON 刪了。

## 對官網的節制

- 同一組查詢條件 10 分鐘內走記憶體快取，不重複打官網（快取上限 200 組，超過淘汰最舊的）
- 所有對外請求排成單一佇列，任何併發情況下間隔都不小於 1.2 秒
- 單次請求 20 秒逾時
- 只查公開的「標案查詢」頁面，不做登入、不大量掃頁

請不要把間隔調短或拿去大量抓取。官網 2025 年起有反爬機制，被擋通常是 403。

## 已知限制

- 官網即時查只涵蓋**招標公告、等標期內**的案子。決標、歷史案件、廠商查詢仍走 g0v / openfun API
- 一次最多 100 筆，關鍵字太寬會被截斷，請縮小範圍
- `parseRows()` 依賴官網表格的**欄位位置**（第 2、3、5、6、7、8、9 欄）。官網改版時要跟著改，
  改完跑 `npm test` 會抓到明顯的解析失敗
- 預算欄位官網有時不公開，會顯示「未提供」（API 回 `budget: 0`）
- `remainingDays` 用 `Math.ceil` 算到截止日 23:59，所以「今天截止」會顯示剩 1 天。前端算法一致，兩邊沒有落差
- Tailwind 已在建置時內嵌；Font Awesome 仍走 CDN，**完全離線時圖示會不見**（功能與版面仍在）
- 前端已拆到 `src/`，但仍大量用 `innerHTML` 字串拼接，所有外來資料一定要過 `esc()`（連結過 `safeUrl()`）
- 發包節奏的系列比對靠名稱正規化，改名重招會認不出來（見上節）
- `test/frontend.test.mjs` 用 `node:vm` 跑 HTML 裡抽出來的 `<script>`，配一組最小 DOM 假物件。
  只測純邏輯，不測畫面；若主程式頂層新增了測試環境沒有的 DOM 呼叫，這支測試會先壞掉——
  在假物件裡補上對應的 stub 即可。
  **跨 realm 的坑**：函式在 vm 沙箱裡建的陣列／物件原型屬於沙箱，`assert.deepEqual`
  會因原型不符而失敗（即使值一模一樣），比較這類回傳值要用 `JSON.stringify`
- `test/ui-smoke.mjs` 補純邏輯測不到的那一半：**用真的滑鼠點擊**驗證渲染出來的東西能不能用。
  要另外裝 `playwright`（`npm i -D playwright && npx playwright install chromium`），
  所以刻意不叫 `*.test.mjs`，`npm test` 不會跑到它。存在的理由是曾經「測試全綠但 9 個按鈕全壞」——
  當時是用 `page.evaluate()` 直接呼叫函式，繞過了真正的 HTML 屬性
- **改版會清掉舊快取**：`pi_daycache` → `pi_daycache2`、`pi_vendor_snap` → `pi_vendor_snap2`。
  舊結構沒有得標／落標的判讀資料，留著只會繼續給錯數字，開頁時會自動移除，公告快取要重抓
