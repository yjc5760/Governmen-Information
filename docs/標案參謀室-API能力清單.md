# 標案參謀室 — 標案 API 實際能力清單（2026-09-11 更新）

做新功能前先看這頁，可以少走冤枉路。以下都是實際打 `pcc-api.openfun.app` 驗過的，
不是推測。資料量：1,455 萬則公告，1999-01-21 起。

## 端點

| 端點 | 回傳 | 每頁 |
| :--- | :--- | :--- |
| `/api/getinfo` | 只有最新／最舊資料時間、公告數。**沒有端點清單** | — |
| `/api/listbydate?date=YYYYMMDD` | 當日全國公告（2026-09-01 實測 1,973 則） | 全部 |
| `/api/listbyunit?unit_id=&page=` | 某機關全期間公告，約 630KB／頁，`total_page` 分頁 | **1000** |
| `/api/searchbytitle?query=&page=` | **只比對標案名稱** | 50 |
| `/api/searchbycompanyname?query=&page=` | 廠商名稱查公告 | **100** |
| `/api/searchbycompanyid?query=&page=` | 統編查公告 | **100** |
| `/api/tender?unit_id=&job_number=` | 單一標案的所有公告紀錄＋完整 detail | — |

> `searchbycompanyname` 曾被記成每頁 20 筆，**是錯的**，實測是 100 筆
> （泰興工程顧問 553 筆 / 6 頁，第 1 頁剛好 100 筆）。
> 這個數字會被拿去算「抓取上限」寫在畫面上，錯了會誤導使用者。

## 關鍵限制（踩過的坑）

1. **沒有「用機關名稱查機關」的端點。** `searchbytitle` 只比對標案名稱——
   拿只出現在機關名裡的字串（`電力修護處`）去查，回傳的每一筆**標題**都還是含該字串。
   所以機關名 → `unit_id` 只能從已抓下來的公告裡累積（見 `pi_agency_index`）。
2. **清單類端點不含金額。** `listbydate` / `listbyunit` / `searchby*` 的 `brief` 只有
   `type`、`title`、`companies{ids,names,id_key,name_key}`。任何金額分析都得逐案打
   `/api/tender`（前端已有 320ms 節流與 `pi_amount_cache`，一個電廠約 10 分鐘）。
3. **連續抓約 15 頁 `listbyunit` 就會被斷線**，錯誤是 `TypeError: Failed to fetch`
   （不是 HTTP 狀態碼，所以不要去看 `resp.status`）。前端因此每輪只抓 15 頁、
   頁間 700ms、單頁失敗退避重試 1.5s→4s→9s，並保留已取得的部分＋提供續抓。
4. **分頁會漂移。** 抓第 N 頁與第 N+1 頁之間官網若新增公告，位移會讓邊界紀錄被重抓
   （台電總公司 30,000 筆裡 34 筆，多數貼齊每千筆邊界）。
   去重鍵要用 `filename + job_number + date + type + 廠商名`：
   **`filename` 單獨不是唯一鍵**（30,000 筆裡重複 1,026 次，會被多筆共用），
   **`job_number + date + type` 也不是**（同案同日可有多則，例如拒絕往來名單一家廠商一則）。
5. `/api/tender` 的回應很大，用 WebFetch 讀會被摘要截斷，判斷欄位要直接看程式碼或原始 JSON。
   **WebFetch 甚至會張冠李戴**：查泰興卻回了中興的 4,681 筆 / 47 頁。
   要看原始 JSON 請用瀏覽器在 `https://pcc-api.openfun.app` 這個 origin 直接 `fetch()`。
6. 機關代碼有層級：`3.13.31` 是台電總公司（40,243 則、41 頁），
   `3.13.31.48`（大林）、`3.13.32.33`（電力修護處）等是其下單位。

## ★ `brief.companies` 不是得標名單（2026-09-11 更正）

**這是目前為止影響最大的一個誤解。** `brief.companies.names` 列的是該案
**所有出現過的廠商**，得標與落標混在一起。整份當成得標名單用的後果，
以 2026-09-01 全日 624 則決標公告實測：

| | |
| :--- | ---: |
| `names` 裡的名字總數 | 1,169 |
| 其中**真的得標** | 725 |
| 其中**落標** | 417 |
| 其中只是英文名變體 | 6 |
| 判不出勝負（長名單未標未得標） | 21 |
| **舊算法的虛增幅度** | **+61%** |

分辨的方法就在同一份 `brief.companies` 裡的 **`name_key`**，
它記錄每個名字是從詳細資料的哪些欄位抓來的，**不必多打任何一次 API**：

| `name_key` 裡的欄位 | 意義 |
| :--- | :--- |
| `決標品項:第N品項:得標廠商N:得標廠商` | 得標 |
| `決標品項:第N品項:得標廠商N(共同投標廠商):得標廠商` | 共同投標且得標 |
| `決標品項:第N品項:未得標廠商N:未得標廠商` | 未得標 |
| `投標廠商:投標廠商N:廠商名稱` | 只知道有投標 |
| `標案內容:廠商名稱` | 拒絕往來公告的當事廠商（**沒有任何得標欄位**） |
| `英文公告:廠商名稱` | 同一家的英文名，**不是另一家公司** |

判讀規則（前端 `splitCompanies()`）：

- `未得標廠商` 這個字串**包含** `得標廠商`，所以要先排除再比對，否則落標會被判成得標
- 多品項的案子同一家可能一項得標、另一項落標（實測有），**只要有一個純得標欄位就算得標**
- 只有 `英文公告:廠商名稱` 的名字是同一家的英文寫法，要整個濾掉，否則廠商數被灌水
- 拒絕往來公告要用 `recBidders()`（全部），不能用 `recVendors()`（得標）——它沒有得標欄位
- 決標公告 624/624 都有 `name_key`，從 `listbydate`、`listbyunit`、`searchby*` 回來的都有

實例（案號 `6331300004`，台電核能火力發電工程處）：

```
泰興工程顧問股份有限公司 (PACIFIC…)  ["投標廠商:投標廠商1:廠商名稱",
                                      "決標品項:第1品項:未得標廠商1:未得標廠商"]  → 落標
吉興工程顧問股份有限公司 (GIBSIN…)   ["投標廠商:投標廠商2:廠商名稱",
                                      "決標品項:第1品項:得標廠商1:得標廠商"]      → 得標
PACIFIC ENGINEERS & CONSTRUCTORS LTD. ["英文公告:廠商名稱"]                        → 英文名變體
```

這一案 `已公告資料:是否共同投標 = 否`。舊程式把這種同場競標當成「共同投標夥伴」，
所以畫面上出現「泰興的常見共同投標夥伴：吉興 19 次」——實際上是**互為對手 19 次**。

## 招標公告 detail 有 85 個欄位

分區前綴：`機關資料:` `採購資料:` `招標資料:` `領投標資料:` `其他:`，
另有 `type` `url` `pkPmsMain` `fetched_at`。對工程顧問直接有用的：

- `招標資料:是否屬統包`
- `招標資料:是否應依公共工程專業技師簽證規則實施技師簽證`
- `招標資料:決標方式`（最低標／最有利標）、`是否訂有底價`、`是否複數決標`、`是否採行協商措施`
- `領投標資料:是否須繳納押標金:押標金額度`、`是否須繳納履約保證金`
- `其他:廠商資格摘要`、`是否訂有與履約能力有關之基本資格:廠商應附具之基本資格證明文件或物品`
- `採購資料:預算金額`、`採購金額級距`、`標的分類`、`後續擴充`
- `其他:履約期限`、`履約地點`、`契約是否訂有依物價指數調整價金規定`
- `採購資料:是否適用條約或協定之採購:是否適用WTO政府採購協定(GPA)` / ANZTEC / ASTEP
- `領投標資料:截止投標`、`開標時間`、`開標地點`

## 決標公告 detail

`總決標金額`、`決標金額`、`決標日期`（前端用 `pickMoney()` 取值，見易錯陷阱第 3 條），
`已公告資料:是否共同投標`、`是否複數決標`，
投標廠商在 `投標廠商:投標廠商N:廠商名稱` 並附 `是否得標`。
複數決標／共同投標只公布一個總額，前端會同時計入每一家，有重複計算風險。

## 由此推導：還做得出來的功能

已做：機關索引累積、發包節奏（週期預測＋流標重招）、標案比較升級、
抓取限流與去重＋不完整標示、投標門檻雷達、拒絕往來廠商查詢、對手常駐追蹤、
機關對比、廠商對比、廠商集中度、落標率分析、**得標／落標判讀**。

**因為落標廠商查得到而新解鎖的（都還沒做）**：

- **投標家數／競爭強度** — 每案有幾家投標，直接算得出來。
  以前這頁寫「做不出來（未得標者不公布）」，**是錯的**
- **對手勝率** — 某家在抓取範圍內投了幾案、中了幾案（已做出 `lostCases`，可再細分機關）
- **誰在跟我搶** — 以吉興為主角跑一次，就是「最常同場競標的對手排行」
- **機關的競爭溫度** — 某機關的案子平均幾家投標，愈少代表門檻愈高或愈封閉
- **同場競標網路圖** — 哪幾家老是一起出現在同一批案子裡

做不出來的：底價金額（只公布有無訂底價）、評選委員名單。
