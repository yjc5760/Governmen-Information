  刻意不叫 `*.test.mjs`，`npm test` 不會跑到它

- 啟動：`start-windows.bat`（Windows）或 `npm start`，開 http://localhost:5178/

## 這個 API 最容易讓人靜靜算錯的地方

1. **`brief.companies.names` 不是得標名單。** 它是該案所有投標廠商，得標落標混在一起。
   2026-09-01 全日 624 則決標公告實測：1,169 個名字裡只有 725 家真的得標，
   舊算法虛增 61%。要用同一份 `brief.companies.name_key` 分勝負（`splitCompanies()`）。
   這個誤解還讓「常見共同投標夥伴」把**同場競標的對手當成夥伴**——
   YJC 是看到「泰興的夥伴：吉興 19 次」才發現不對的。
2. **`X` 與 `X是否公開` / `X:remind` 成對出現。** 任何子字串比對的取值都會撈到伴生欄位。
   決標公告的 `已公告資料:預算金額是否公開`（值「是」）排在 `已公告資料:預算金額` 之前
   → `parseMoney('是')` = 0 → 落標率永遠算不出來。金額一律走 `pickMoney()`。
3. **公告類型大量共用子字串。** `更正決標公告` 含「決標公告」（虛增 20.9%），
   `無法決標公告` 含「決標」。一律走集中的 `isAward()` / `isFailedAward()` / `isTender()`。
4. **分頁會漂移。** 去重鍵必須是複合鍵，`filename` 單獨不唯一（會被多筆共用）。
5. **API 對訪客限流**（約 10 次額度、每 3 秒補 1，超過回 429；429 沒 CORS 標頭，所以網頁只看到 `Failed to fetch`）。
   以前誤記成「listbyunit 連抓約 15 頁就斷線」。2026-10-07 起由 `api()` 共用節流處理。
6. **`searchbycompanyname` 每頁 100 筆**（一度被記成 20 筆，是錯的）。

貫穿以上的設計原則：**寧可標明「資料不完整」，也不要靜靜給出看似精確的錯數字。**
不完整就顯示「已取得 X / 官方 Y」、樣本數、涵蓋率警告；預測不規律就標「不規律」並淡化；
分不出得標落標時公告卡片只寫中性的「廠商」，不假裝知道誰得標。

## 2026-09-11 這次改了什麼

## 2026-09-11 第二批：排除契約變更 ＋ 流標機會清單

YJC 提了七條情報軸線，逐條打真實 API 查證後的判定見 API 能力清單。這批做了兩件：

**① 排除契約變更**（`isAmendment()` / `isAwardRec()`）。
它本來污染決標件數、廠商排行、落標率、機關快照。台電核火處 27.9% 的決標公告是契約變更。

**② 流標機會清單**（機關洞察，`flopBlock()`）。
同一案號串出「招標 → 流標 → 重招 → 決標」序列，分成「還沒成案」（機會）與
「已重招決標」（看當初拖多久）。序列不打 API；流標理由、是否沿用案號續招、
各輪預算變化在 detail 裡，做成按鈕**只對未成案的前 30 筆**逐案抓，存在 `pi_flop_detail`。
判定成案的規則是「最後一次流標**之後**才出現的決標」——之前的決標是上一輪的事，
而且契約變更不算成案。

順手修掉一個潛在崩潰：`amtKey()` 在沒開機關時會讀 `unitData.unit_id` 而炸掉。

## 2026-09-11 第三批：前置公告雷達（插隊做，因為前兩個判定是錯的）

YJC 問「有公開閱覽或公開徵求的標案嗎」，一查才發現**我前面兩個判定都錯了**：

- 錯了①「這個 API 沒有標案預告，軸線 1 走不通」——`招標文件公開閱覽公告資料`
  就是實質預告（招標文件草案公開供閱覽），`公開徵求廠商提供參考資料` 是 RFI、更早。
  我只掃了類型名稱裡有沒有「預告」兩個字。
- 錯了②「軸線 3 資格條款逆向工程做不到」——**公開閱覽公告的廠商資格摘要有量化特定資格**，
  招標公告的同名欄位才是樣板文字。而且連預算金額都有，招標前約四週就看得到。

而這兩種公告本來被 `TYPE_NOT_TENDER` 排除在 `isTender()` 之外（這件事沒錯，
它們確實不是招標），但整個程式**只做到排除、沒人去看**，於是最有價值的公告被當雜訊。

做出來的是機關洞察最上面的**前置公告雷達**（`preTenderBlock()`）：

- 分三區：**還沒招標**（時間窗在這裡）／**日期對不起來**（反常資料，不當成機會）／
  **已進入招標**（用來校準時間窗）
- 推估招標區間用**這個機關自己**的間隔分布（四分位），中位數實測 28 天；
  樣本少於 5 筆就不推估。逾期會說可能招標在即、計畫展延、改案號重辦，
  **或只是那則招標公告還沒抓到**
- 「補預算與資格條款」只對尚未招標的前 30 筆逐案抓，特定資格用 `splitQual()`
  拆出來以紅框突出（沒有特定資格也明說，那代表門檻低而不是資料缺漏）
- 快取 `pi_pre_detail`

## 2026-09-11 第四批：抓取深度可設定 ＋ 兩個公平性問題

YJC 問「已抓取 300 筆是只抓 300 筆嗎、這值可以設定嗎」，順著這個問題查出三件事：

**① 空頁被當成抓完（靜默截斷重演）。** `fetchVendor` 原本 `if(!rows.length) break;`，
但實測連續抓時會偶發回空頁——中興第 9 頁回 0 筆導致只拿到 800 筆（實際 5,482 筆）、
亞新第 16 頁回 0 筆導致拿到 1,500 而不是 1,507。單獨重抓同一頁又有資料。
畫面上完全看不出來。現在空頁會重試，並把停止原因記進快照
（`done` / `cap` / `empty` / `fail`）顯示出來。

**② 3 頁（300 筆）過度保守。** 那是從「每頁 20 筆」的錯誤認知與 `listbyunit`
會斷線的經驗延伸來的，但 `searchbycompanyname` 每頁只 127KB（`listbyunit` 是 630KB），
連抓不會斷。實測抓到底：亞新 16 頁 15.3 秒、中興 55 頁約 55 秒、多數顧問公司不到 10 秒。
現在深度可設定（3／6／12／抓到底，上限 60 頁），預設 6 頁，畫面會顯示預估秒數。

**③ 涵蓋率不同的件數被並排比。** 截圖裡三家都「已抓 300 筆」看似公平，實際涵蓋率是
泰興 54%、巨廷 36%、亞新 20%，而**得標件數 152 被標成綠色「最佳」**——那只代表巨廷在
它那 36% 樣本裡得標多。現在欄位分成全歷史類／比例類／件數類，件數類在涵蓋率落差
超過 1.25 倍時停掉「最佳」標示、標「不可比」，並在表格上方寫出涵蓋率區間與修法。

## 2026-10-07：「第 24 頁失敗」查明是 API 限流，改成共用節流

YJC 抓中興工程顧問「抓到底」時卡在第 24 頁失敗。到 `pcc-api.openfun.app` 同源實測：

- 訪客限流是 token bucket：**閒置後約 10 次、每 3 秒補 1 次**（約每分鐘 20 次），超過回 429
- **429 沒有 CORS 標頭** → 從 localhost／GitHub Pages 只看得到 `TypeError: Failed to fetch`。
  以前的「listbyunit 連抓 15 頁就斷線」也是同一件事
- 舊程式頁間只隔 400ms、重試 1.2→3→7 秒，額度用完後重試也常撞牆，最後放棄
- 逐案補決標金額、補前置／流標詳情、更新追蹤也一樣會撞，超過額度的案子被記成失敗

**改法**（`src/js/03-api.js`）：所有 API 呼叫排隊、共用客戶端額度（容量 8、每 3.2 秒補 1）；
撞到 429 或 Failed to fetch 就額度歸零、等 6→12→20→30 秒再試；翻頁與進度列會寫出
「放慢速度避免被限流」或「API 限流，等 N 秒」，沒有進度列的地方用提示。有 token 時不預先放慢。
機關每輪上限 15 → 30 頁。各迴圈原本的固定間隔改為 0。新增 5 項測試（共 79 項）。

**實測**（從 GitHub Pages 跨來源）：中興 55 頁、5,498 筆一次抓完，**零次撞牆**，151 秒。
代價是大量抓取變慢——這是 API 的上限，只有申請 token 才能更快。
