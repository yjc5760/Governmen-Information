# 標案參謀室 — 專案現況（2026-09-11）

本機位置：`D:\自用情報網站`（YJC 的電腦 n924-x64）。改版走 git，不要再複製備份檔。
API 能力與踩過的坑另見 `docs/標案參謀室-API能力清單.md`——**做新功能前先看那頁**。

## 組成

- `標案參謀室.html` — 單檔前端，八個頁面，資料全在瀏覽器 localStorage
- `server.js` — 本機 proxy（v1.1.0）：把網頁服務出去 + 代查政府電子採購網官網
- `test/parse.test.mjs`（5 項，server.js）＋ `test/frontend.test.mjs`（44 項，
  用 node:vm 跑 HTML 裡的 script，零額外依賴）→ `npm test` 共 **49 項**
- `test/ui-smoke.mjs` — 畫面實測，**用真的滑鼠點擊**。需自行裝 playwright，
  刻意不叫 `*.test.mjs`，`npm test` 不會跑到它
- `build/` — 打包成單一 Windows exe（Node SEA），見 `docs/標案參謀室-打包exe筆記.md`
- 啟動：`start-windows.bat`（Windows）或 `npm start`，開 http://localhost:5178/

## 這個 API 最容易讓人靜靜算錯的地方

1. **`brief.companies.names` 不是得標名單。** 它是該案所有投標廠商，得標落標混在一起。
   2026-09-01 全日 624 則決標公告實測：1,169 個名字裡只有 725 家真的得標，
   舊算法虛增 61%。要用同一份 `brief.companies.name_key` 分勝負（`splitCompanies()`）。
   這個誤解還讓「常見共同投標夥伴」把**同場競標的對手當成夥伴**——
   YJC 是看到「泰興的夥伴：吉興 19 次」才發現不對的。
2. **`X` 與 `X是否公開` / `X:remind` 成對出現。** 任何子字串比對的取值都會撈到伴生欄位。
   決標公告的 `已公告資料:預算金額是否公開`（值「是」）排在 `已公告資料:預算金額` 之前
   → `parseMoney('是')` = 0 → 落標率永遠算不出來。金額一律走 `pickMoney()`。
3. **公告類型大量共用子字串。** `更正決標公告` 含「決標公告」（虛增 20.9%），
   `無法決標公告` 含「決標」。一律走集中的 `isAward()` / `isFailedAward()` / `isTender()`。
4. **分頁會漂移。** 去重鍵必須是複合鍵，`filename` 單獨不唯一（會被多筆共用）。
5. **`listbyunit` 連抓約 15 頁就被斷線**（`TypeError: Failed to fetch`，不是 HTTP 狀態碼）。
6. **`searchbycompanyname` 每頁 100 筆**（一度被記成 20 筆，是錯的）。

貫穿以上的設計原則：**寧可標明「資料不完整」，也不要靜靜給出看似精確的錯數字。**
不完整就顯示「已取得 X / 官方 Y」、樣本數、涵蓋率警告；預測不規律就標「不規律」並淡化；
分不出得標落標時公告卡片只寫中性的「廠商」，不假裝知道誰得標。

## 2026-09-11 這次改了什麼

得標／落標判讀（`splitCompanies` / `recVendors` / `recBidders`），連帶修正：

- 機關洞察的得標廠商排行、市場集中度 CR/HHI（原本把落標廠商算成得標）
- 廠商快照的「決標件數」→ 拆成**得標件數**與**落標件數**，加「抓取範圍內得標率」
- 「常見共同投標夥伴」→ 拆成**共同得標夥伴**（同案一起得標）與
  **常同場競標對手**（同案出現但不是一起得標）
- 拒絕往來名單改用 `recBidders()`（該類公告的廠商掛在 `標案內容:廠商名稱`，沒有得標欄位）
- 公告卡片標出「得標／投標廠商／廠商」三種狀態
- 濾掉只出現在 `英文公告:廠商名稱` 的英文名變體（原本被當成另一家公司）
- **快取改版**：`pi_daycache` → `pi_daycache2`、`pi_vendor_snap` → `pi_vendor_snap2`，
  舊鍵開頁時自動移除（舊結構沒有勝負資料，留著只會繼續給錯數字）。公告快取要重抓

## 2026-09-11 第二批：排除契約變更 ＋ 流標機會清單

YJC 提了七條情報軸線，逐條打真實 API 查證後的判定見 API 能力清單。這批做了兩件：

**① 排除契約變更**（`isAmendment()` / `isAwardRec()`）。
它本來污染決標件數、廠商排行、落標率、機關快照。台電核火處 27.9% 的決標公告是契約變更。

**② 流標機會清單**（機關洞察，`flopBlock()`）。
同一案號串出「招標 → 流標 → 重招 → 決標」序列，分成「還沒成案」（機會）與
「已重招決標」（看當初拖多久）。序列不打 API；流標理由、是否沿用案號續招、
各輪預算變化在 detail 裡，做成按鈕**只對未成案的前 30 筆**逐案抓，存在 `pi_flop_detail`。
判定成案的規則是「最後一次流標**之後**才出現的決標」——之前的決標是上一輪的事，
而且契約變更不算成案。

順手修掉一個潛在崩潰：`amtKey()` 在沒開機關時會讀 `unitData.unit_id` 而炸掉。

### 還沒做的軸線（依建議順序）

3. **設計標 → 施工標時窗**：用決標公告的 `履約起迄日期` 推算，發包節奏的名稱正規化可沿用。
   必須標明是**推估**，設計標展延／計畫喊停／拆包都會讓它失準
4. **決標比例分布**：按機關 × 標的分類 × **招標方式**分群（招標方式是最關鍵那一維——
   台電核火處抽樣的決標／預算比全在 0.96–1.00，因為多數是限制性招標議價）。
   要逐案補金額，成本最高
5. **標的分類熱圖**：低成本，但業務集中在 `8672 工程服務`，邊際價值不如前面幾條

**判定為不做的兩條**：資格條款逆向工程（API 給不出實績金額／技師人數，
做出來只是投標門檻雷達的重包裝）、單價資料庫（API 沒有 MW／公里／座等規模欄位，
用標案名稱正則猜會產生一條看起來很專業的假成本基準）。
