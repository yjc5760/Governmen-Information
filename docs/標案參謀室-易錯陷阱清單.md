# 標案參謀室 — 易錯陷阱清單

**改這個專案的程式前先看這頁。** 這裡每一條都是實際踩過、而且**不會報錯、只會靜靜給錯答案
或靜靜失效**的問題。API 能力見 `docs/標案參謀室-API能力清單.md`。

貫穿全部的原則：**寧可標明「資料不完整」，也不要靜靜給出看似精確的錯數字。**

---

## 1. 事件屬性裡不可直接用 `JSON.stringify`

把字串當參數塞進 `onclick` / `onchange` 時**一定要用 `jsArg()`**。
屬性是雙引號包的，而 `JSON.stringify` 產生的字串**也帶雙引號**：

```
onchange="toggleVsnapSel("亞新工程顧問",this.checked)"
                         ↑ HTML 解析器在這裡就把屬性結束掉
```

handler 變成語法錯誤，**按鈕完全沒反應，主控台也不一定看得到錯誤**。

實際發生過：一次壞掉 **9 處**——廠商對比與機關對比的核取方塊、快速加入對手、
更新／移除、刪快照、機關挑選（2 處）、載入失敗重試。而且畫面看起來很正常，
因為**核取方塊視覺上仍會打勾**（那是瀏覽器預設行為，跟 handler 無關）。

**怎麼判斷中招**：看畫面上的計數有沒有跟著動。當時標題寫「目前有 4 份廠商快照。」
卻沒有「，已勾 N 家」，就代表程式眼中一個都沒勾到。

`test/frontend.test.mjs` 有一支**掃原始碼**的測試守著，`test/ui-smoke.mjs` 則用
**真的滑鼠點擊**再守一次（實測把 `jsArg` 換回 `JSON.stringify`，ui-smoke 會失敗）。

相關的第二個坑：**勾選會重繪整個 `<details>`**，若只用 `sel.length>=2` 決定要不要加
`open`，使用者勾第一個時面板會當場收起來。重繪前要先讀目前的展開狀態沿用。

## 2. 公告類型名稱大量共用子字串

隨手 `indexOf` 一定出錯。以台電總公司 `3.13.31` 實測 30,000 筆的分布為證：

| 誤判 | 後果 |
| :--- | :--- |
| `更正決標公告` 含 `決標公告` | 決標數、廠商件數、集中度、落標率**虛增 20.9%**（多 2,709 筆） |
| `無法決標公告` 含 `決標` | 「只看決標公告」多列 **2,937 筆流標案** |
| `撤銷無法決標公告` 含 `無法決標` | 被當成流標，語意相反 |
| `限制性招標(經公開評選…)公告` **不含** `招標公告` | **1,109 筆招標被漏掉** |
| `招標文件公開閱覽公告資料公告` 含 `招標` | 那是招標前置作業，不是招標 |

**規則**：一律走集中的 `isAward` / `isFailedAward` / `isTender` / `isDebarred`，
不要在別處自己寫 `indexOf`。而且「統計」與「顯示」定義不同，刻意分兩組不可互用——
顯示用的 `isAwardNotice` / `isTenderNotice` 含更正（更正公告也是該類別的資訊），
統計用的一案一筆、排除更正與撤銷。

## 3. 欄位名稱也成對出現：`X` 與 `X是否公開` / `X:remind`

決標公告的鍵順序把 `已公告資料:預算金額是否公開`（值是「**是**」）排在
`已公告資料:預算金額` **之前**。用子字串比對的 `pick()` 先撞到「是」，
`parseMoney('是')` = 0。

後果：落標率與「決標／預算比」**永遠算不出來**，而且打開決標公告的標案詳情時
**「採購預算」顯示「是」**。

`總決標金額` 同樣有陷阱：旁邊有 `總決標金額:remind`（中文說明、無數字）與
`投標廠商:投標廠商N:決標金額`（單一廠商金額，不是總額）。

**規則**：金額一律走 `pickMoney()`（鍵尾完全相符、跳過說明類欄位、值須為正數），
決標公告沒有預算時用 `pickMoneyAcross()` 回頭找招標公告。

## 4. localStorage 只有約 5 MB，滿了會讓所有寫入靜默失敗

公告快取是唯一會長到 MB 級的（全國一天約 1,000 則，14 天就可能超過整個配額）。
原本 `persistDayCache()` 的設計是「寫到失敗為止」，也就是刻意填滿配額，
於是其他 30 幾個寫入點全部靜默失敗——**加入追蹤會顯示成功、計數會增加、重載後消失**。
縮小的寫入還會成功，所以症狀是「可以刪不能加」，看起來像隨機 bug。

**規則**：不要直接 `localStorage.setItem`，不要忽略 `LS.set` 的回傳值。
`LS.set` 會先試寫 → 從公告快取回收空間 → 重試 → 還是失敗才明確告知（依鍵節流 30 秒）。
使用者動作寫入失敗時**記憶體要一起回滾**，否則畫面顯示「已追蹤」但重載就不見。

## 5. 分頁會漂移，而 `filename` 不是唯一鍵

抓第 N 頁與第 N+1 頁之間官網若新增公告，位移會讓邊界紀錄被重抓
（台電總公司 30,000 筆裡 34 筆）。

- **`filename` 單獨不唯一**：30,000 筆裡重複 1,026 次，會被多筆共用
- **`job_number + date + type` 也不唯一**：同案同日可有多則（拒絕往來名單一家廠商一則）

**規則**：去重用複合鍵 `filename + job_number + date + type + 廠商名`，
實測與整筆 JSON 比對抓到完全相同的 34 筆，但快 4 倍。

## 6. 連續抓約 15 頁 `listbyunit` 就會被斷線

錯誤是 `TypeError: Failed to fetch`，**不是 HTTP 狀態碼**，所以不要去看 `resp.status`。
原本整個分頁迴圈包在一個 try/catch 裡，第 16 頁一失敗就把前面 15,000 筆全丟掉。

**規則**：每輪上限 15 頁、頁間 700ms、單頁失敗退避重試（1.5s→4s→9s），
失敗也保留已取得的部分並提供續抓。

## 7. 「靜默截斷」比報錯更糟

25 頁上限對 41 頁的機關會直接截掉，而廠商排行、金額合計、發包節奏全部只算那一部分，
畫面上卻完全沒說。

**規則**：不完整就顯示「已取得 X / 官方 Y（第 1–p / t 頁）」、樣本數、涵蓋率警告，
並附續抓按鈕。發包節奏另有獨立警示（公告新到舊排序，未抓完＝缺早年資料）。

## 8. 預測不規律就要說不規律

台電有個案子 2025/08/14 流標、2026/02/04 重招，相隔 174 天。原本按「每曆年取最早一次」
去重，這兩筆分屬不同曆年而雙雙留下，**174 天被當成「半年一次的週期」**，
還跟 5/5 命中的年度案並列同一張表。

**規則**：用「距上一次不到 240 天視為同一輪」收攏，不看曆年；只有間隔接近
365／730／1095 天才標規律，其餘標「不規律」、淡化、排到最後、不計入「120 日內」統計。
**刻意不設「半年」類**——單一個 150~250 天的間隔無法與流標重招區分。

## 9. 測試環境的跨 realm 陷阱

`test/frontend.test.mjs` 用 `node:vm` 跑 HTML 裡抽出來的 `<script>`。
沙箱裡建立的陣列／物件原型屬於沙箱 realm，`assert.deepEqual`（strict 模式即
`deepStrictEqual`）會因原型不符而失敗，**即使值一模一樣**。

**規則**：比較這類回傳值用 `JSON.stringify`。

## 10. `brief.companies.names` 含落標廠商，不是得標名單

**目前為止影響最大的一個誤解。** 名單裡得標與落標混在一起。
2026-09-01 全日 624 則決標公告實測：1,169 個名字裡只有 **725 家真的得標**、
417 家落標，**得標件數虛增 61%**。

一次污染了五個地方：機關洞察的得標廠商排行、市場集中度 CR/HHI、
廠商快照的決標件數與主要機關、拒絕往來名單的得標交叉比對，
以及最明顯的——**「常見共同投標夥伴」把同場競標的對手當成夥伴**。

YJC 是看到「泰興工程顧問的常見共同投標夥伴：吉興工程顧問（19 次）」覺得不對才問的。
查案號 `6331300004`（台中電廠第二期新建燃氣機組，台電核能火力發電工程處）：
`已公告資料:是否共同投標 = 否`，泰興投標落標、吉興投標得標。**是對手，不是夥伴。**

分辨方法在同一份 `brief.companies` 的 `name_key`，**不必多打任何一次 API**：

| `name_key` 欄位 | 意義 |
| :--- | :--- |
| `決標品項:第N品項:得標廠商N:得標廠商` | 得標 |
| `決標品項:第N品項:得標廠商N(共同投標廠商):得標廠商` | 共同投標且得標 |
| `決標品項:第N品項:未得標廠商N:未得標廠商` | 未得標 |
| `投標廠商:投標廠商N:廠商名稱` | 只知道有投標 |
| `標案內容:廠商名稱` | 拒絕往來公告的當事廠商（**沒有得標欄位**） |
| `英文公告:廠商名稱` | 同一家的英文名，**不是另一家公司** |

三個容易再踩一次的細節：

1. **`未得標廠商` 這個字串包含 `得標廠商`。** 先排除「未得標」再比對，
   否則落標會被判成得標——這正是第 2 條那個坑換了個地方重演
2. **多品項的案子同一家可能一項得標、另一項落標**（2026-09-01 實測有），
   規則是**只要有一個純得標欄位就算得標**
3. **拒絕往來公告要用 `recBidders()`**，不能用 `recVendors()`。
   它的廠商掛在 `標案內容:廠商名稱`，沒有任何得標欄位，用得標判斷會回空陣列，
   整份停權名單靜靜消失

**規則**：一律走 `splitCompanies()` →
`recVendors()`（得標，統計用）／`recBidders()`（全部，顯示與拒絕往來用）。
分不出勝負時公告卡片只寫中性的「廠商」，不要假裝知道誰得標。

改這條時**快取結構也要改版**（`pi_daycache2` / `pi_vendor_snap2`），
舊快取沒有勝負資料，留著只會繼續給錯數字。


## 11. 契約變更也是一則獨立的決標公告

「○○採購案第 3 次契約變更」在 API 眼裡就是一則 `決標公告`，有自己的案號、
自己的決標金額與預算金額——而那是**變更金額**，不是原案金額。

實測佔決標公告的比例，**機關之間差到天南地北**：

| 機關 | 決標公告 | 其中契約變更 | 佔比 |
| :--- | ---: | ---: | ---: |
| 台電核能火力發電工程處 | 610 | 170 | **27.9%** |
| 全國 2026-09-01 全日 | 624 | 30 | 4.8% |
| 國立臺灣科學教育館 | 268 | 6 | 2.2% |
| 台電電力修護處 | 201 | 0 | 0% |

**偏偏在新建工程單位最嚴重**，也就是最常看的那些機關。不排除的話：決標件數灌水、
廠商排行灌水（同一家同一案被算三四次）、落標率被往 1.0 拉——議價後的變更案
決標金額常常等於底價。

**規則**：統計走 `isAwardRec(r)`（= `isAward(type)` 且不是契約變更），
不要只用 `isAward(recTy(r))`。

三個判斷上的細節：

1. **標題比對就夠準**。台電核火處那 170 則逐筆看過沒有誤判，
   `…契約變更(第4次)`、`…之契約變更`、`Amendment No.2` 這些寫法都在 `契約變更` 之內
2. **不要改成比對「第 N 次契約變更」**。實測有標題用全形康熙部首 `⼗`（U+2F17）
   而不是 `十`（U+5341）：`⼤潭8&9號機主發電設備採購案第⼗一次契約變更…`，
   序數比對會漏掉 13 則
3. **刻意不納入「變更設計」與「增購」**。`○○工程變更設計委託技術服務` 是真的案子，
   `增購試運轉期間必要之備品` 也是真的採購——把它們排除掉會漏案，比灌水更糟

契約變更本身是有用的情報（追加預算、工項增加），所以是**從統計裡排除**而不是丟掉，
畫面上要看得到它們還在。

## 12. 招標公告之前還有兩種公告，一度被當成雜訊

`TYPE_NOT_TENDER` 把 `公開閱覽` 與 `徵求廠商提供參考資料` 排除在 `isTender()` 之外——
**這件事本身沒錯**（它們確實不是招標，不該計入招標數），錯的是整個程式**只做到排除**，
沒有人去看它們，於是最有價值的兩種公告被當雜訊丟了半年。

| 公告類型 | 是什麼 |
| :--- | :--- |
| `招標文件公開閱覽公告資料` | 機關把**招標文件草案**公開供廠商閱覽並收意見，約四週後正式招標 |
| `公開徵求廠商提供參考資料` | RFI，通常還在**寫規範**的階段，更早 |

實測台電的使用情況與時間窗：

| | 台電核火處（1,187 則） | 台電總公司（2,000 則） |
| :--- | ---: | ---: |
| 公開閱覽 | 38 | 44 |
| 公開徵求 | 16 | 213 |
| 有前置公告的案號 | 47 | 222 |
| 其中後來確實招標 | 35 | 33 |
| **前置→招標中位數** | **28 天**（四分位 21–45） | **28 天** |

而且 `招標文件公開閱覽` 的 detail 有**招標公告給不出來**的兩樣東西：

1. **`標案內容:預算金額`** —— 招標前就知道預算
2. **`標案內容:廠商資格摘要`** —— 這裡是**量化的特定資格**，不是樣板文字

對比同一個概念在兩種公告裡的差別：

```
招標公告   其他:廠商資格摘要
  「廠商登記或設立之證明投標廠商之基本資格須符合以下任一資格：
    具公司登記具商業登記廠商納稅之證明…」        ← 樣板，毫無鑑別力
  其他:是否訂有與履約能力有關之特定資格:… 
  　「1.具有相當經驗或實績。」                    ← 也是樣板

公開閱覽公告   標案內容:廠商資格摘要
  「基本資格:經中華民國政府機關核准設立之工程技術顧問公司…
    特定資格:投標廠商於截止投標日前二十年內具有 1 部 44 萬瓩(含)以上
    之發電機組規劃設計整合之經驗，且該機組業已商轉，或前述期間累積
    110 萬瓩(含)以上…」                          ← 真正的門檻
```

**規則**：前置公告走 `isPreview()` / `isRFI()` / `isPreTender()`，
資格條款走 `splitQual()` 拆出特定資格（特定資格才有鑑別力；**沒有特定資格本身也是訊號**，
代表門檻低、開放程度高，不要當成「資料缺漏」）。

三個踩過的細節：

1. **`經公開評選或公開徵求之限制性招標公告` 含「公開徵求」四個字**，
   但它是**招標公告**。`isRFI()` 必須比對完整的 `徵求廠商提供參考資料`，
   不可以只比對「公開徵求」——又是第 2 條那個坑換地方重演
2. **類型名稱有加不加「公告」兩種寫法**：`招標文件公開閱覽公告資料公告` 與
   `招標文件公開閱覽公告資料` 都存在，`公開徵求廠商提供參考資料` 也一樣，
   所以用 `indexOf` 比對核心字串而不是等號
3. **有招標日早於前置公告日的反常資料**（實測相差 −12 天）。
   這種案子「有招標公告、只是日期對不起來」，**不可以顯示成還沒招標的機會**，
   也不可以拿那個負數去算時間窗——要單獨列一區並說明原因

推估區間一律標明「推估不是公告」，並顯示樣本數；樣本少於 5 筆就不推估。
逾期（超過該機關 Q3）要主動說可能是招標在即、計畫展延、改案號重辦，
**或只是那則招標公告還沒抓到**——最後這個可能性最常被忽略。

## 13. 空頁不等於抓完——`searchbycompanyname` 連續抓會偶發回空

`fetchVendor` 原本寫成：

```js
if(!rows.length || (tp && p>=tp)) break;      // ← 空頁當成抓完
```

**實測連續抓的時候，偶爾會回一個空的 `records`，單獨重抓同一頁又有 100 筆。**
兩次都親眼遇到：

| 廠商 | 現象 | 單獨重抓 |
| :--- | :--- | :--- |
| 中興工程顧問（5,482 筆 / 55 頁） | 連抓時第 9 頁回 0 筆，迴圈以為抓完，只拿到 800 筆 | 第 9 頁穩定回 100 筆 |
| 亞新工程顧問（1,507 筆 / 16 頁） | 連抓時第 16 頁回 0 筆，拿到 1,500 筆 | 第 16 頁回 7 筆 |

不是 API 有筆數上限——中興第 55 頁單獨抓三次都穩定回 82 筆（5482 ÷ 100 = 54.82，
剛好是餘數），所以最後一頁的餘數是拿得到的。

這是**第 7 條「靜默截斷」在新的地方重演**，而且更難發現：畫面上顯示「已抓 800 筆」
看起來完全正常，沒有任何錯誤訊息。

**規則**：只要 `total_pages` 說後面還有，空頁就先重試，確認過才認定結束。
而且要把**停止原因**記進快照（`stop.reason`）並顯示出來：

| `reason` | 意思 |
| :--- | :--- |
| `done` | 真的抓到最後一頁 |
| `cap` | 到達使用者設定的頁數上限 |
| `empty` | 那一頁重試後仍是空的 |
| `fail` | 那一頁重試多次仍失敗 |

「已抓 N 筆」單獨出現沒有意義，一定要配上「為什麼只有 N 筆」。

### 順帶修正：每頁筆數與抓取成本

`searchbycompanyname` **每頁 100 筆**（一度記成 20 筆），而且每頁只約 **127KB**，
不是 `listbyunit` 的 630KB，所以**不會像 `listbyunit` 那樣連抓 15 頁就斷線**。
實測抓到底的成本：

| 廠商 | 筆數 / 頁數 | 抓到底耗時 |
| :--- | ---: | ---: |
| 吉興工程顧問 | 284 / 3 | 約 3 秒 |
| 泰興工程顧問 | 553 / 6 | 約 6 秒 |
| 巨廷工程顧問 | 823 / 9 | 約 9 秒 |
| 亞新工程顧問 | 1,507 / 16 | **實測 15.3 秒** |

原本寫死 3 頁（300 筆）過度保守——那是從「每頁 20 筆」的錯誤認知
與 `listbyunit` 會斷線的經驗延伸來的。現在深度可設定（3／6／12／抓到底，
上限 60 頁），預設 6 頁。

## 14. 涵蓋率不同的兩家，件數不可以並排比

YJC 截圖裡三家都「已抓取 300 筆」，看起來很公平，實際上是：

| 廠商 | 官方總筆數 | 已抓 | 涵蓋率 |
| :--- | ---: | ---: | ---: |
| 泰興工程顧問 | 553 | 300 | **54%** |
| 巨廷工程顧問 | 823 | 300 | 36% |
| 亞新工程顧問 | 1,507 | 300 | **20%** |

**得標件數 152 被標成綠色「最佳」**，但那只代表巨廷在它那 36% 的樣本裡得標多，
跟它是否比較活躍無關。相同筆數 ≠ 相同涵蓋率。

**規則**：欄位要分「全歷史類／比例類／件數類」三種。
件數類（得標件數、落標件數、更正公告、涉及機關數、共同得標夥伴數）
在各家涵蓋率落差超過 `VSNAP_FAIR_RATIO`（1.25 倍）時：

1. 停掉「最佳」標示
2. 欄位名稱旁標「不可比」
3. 表格上方出現橫幅，寫出涵蓋率區間，**並告訴使用者怎麼修**
   （把抓取深度調成「抓到底」後各家重新更新一次）

比例類（得標率、最大機關佔比、涵蓋率）與全歷史類（官方總筆數）不受影響，
那些本來就可比。

## 15. `esc()` 必須連引號一起跳脫（網頁公開後就是 XSS）

舊版 `esc()` 借 `div.textContent → innerHTML` 跳脫，只處理 `& < >`，**不處理引號**。
文字節點裡沒事，但有三處把資料放進屬性：

```js
'title="'+esc(r.v)+'"'          // 標案詳情的長欄位
'value="'+esc(unitVendorQ)+'"'  // 機關頁的廠商搜尋框
'href="'+esc(x.link)+'"'        // 官網即時查的連結
```

資料裡一個 `"` 就能跳出屬性、塞進 `onmouseover=…`。資料來源包括 API、proxy 解析的官網表格，
以及**別人給你的備份檔**（匯入就會進 localStorage）。網頁放上公開網址之後，這就是真的漏洞。
現在 `esc()` 改成純字串取代、五個字元都處理（也比建 DOM 節點快），
連結另外過 `safeUrl()`，只放行 `http(s)://`——`javascript:` 網址就算跳脫了引號，點下去照樣執行。

## 16. Tailwind 內嵌後，class 必須寫完整；而且「測試會過」不代表樣式對

建置時 Tailwind 只掃**字面上出現過的 class 名稱**。`'bg-'+tone+'-100'` 掃不到，
畫面就沒顏色（前置公告雷達與流標清單的標籤原本就是這樣寫）。改成完整名稱，
`npm run build` 也會點名可疑寫法。

反過來的坑：`test/ui-smoke.mjs` 以前在**連不到 CDN 的環境**跑，Tailwind 根本沒載入，
`.hidden` 沒有樣式，於是「直接塞 `unitData` 再 `renderAgencyDetail()`」雖然沒拿掉
`#agencyDetail` 的 `hidden` 也照樣點得到。樣式內嵌之後這個漏洞才現形。
**畫面測試要在樣式真的生效的狀態下跑**，否則可見性相關的檢查全是假的。

## 17. 幾萬筆資料下，任何「每筆 × 每筆」都會爆

`buildFailed()` 原本對每則流標把全部招標掃一遍（而且每對都重算一次 `seriesKey` 的九道正規表示式）。
合成的 4 萬則機關資料實測：**一次重繪 22 秒**，切換期間、排序都要再等 22 秒。
改成先按系列分組、組內排序、二分搜尋，再加上 `seriesKey` 依標題快取 → 約 0.4 秒，
輸出逐字相同（有測試拿舊寫法當參考答案比對，含同日多筆的情況）。
同類的小坑：只為了取最早／最晚日期就把 4 萬個 `Date` 整串排序——用 `recDateRange()` 掃一遍就好。

順帶：**不要用 `toISOString().slice(0,10)` 取日期**。它換算成 UTC，
台灣的本地午夜會變成前一天（機關頁的起訖日、備份檔名都早一天）。用 `ymdDash()`。

## 修改流程建議

1. 網頁改 `src/`，`npm run build` 產生 `標案參謀室.html`，再 `npm test`（74 項，含用真實類型分布驗證決標數、用真實 `name_key` 驗證勝負判讀、
   以及掃原始碼的防護測試）
2. 畫面行為跑 `node test/ui-smoke.mjs`（需自行裝 playwright），它**用真的滑鼠點擊**。
   不要用 `page.evaluate` 直接呼叫函式——**第 1 條那個 bug 就是這樣溜過去的**：
   測到了函式，沒測到渲染出來的屬性。
   mock 也要用**真實形狀**（每頁筆數、混雜的公告類型、`names` 含自己與落標廠商且有英文後綴）
3. 數字類功能要**先手算預期值再比對**，不要看到有數字就當它對
4. 加防護測試時，**要實際把 bug 放回去確認測試會失敗**，不會失敗的測試沒有價值

   這樣失敗時檔案完全沒動，不會留下改一半的狀態

   （查泰興回了中興的數字）。用瀏覽器在 `https://pcc-api.openfun.app` 這個 origin 直接 `fetch()`
