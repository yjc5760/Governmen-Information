# 標案參謀室 — 易錯陷阱清單

**改這個專案的程式前先看這頁。** 這裡每一條都是實際踩過、而且**不會報錯、只會靜靜給錯答案
或靜靜失效**的問題。API 能力見 `docs/標案參謀室-API能力清單.md`。

貫穿全部的原則：**寧可標明「資料不完整」，也不要靜靜給出看似精確的錯數字。**

---

## 1. 事件屬性裡不可直接用 `JSON.stringify`

把字串當參數塞進 `onclick` / `onchange` 時**一定要用 `jsArg()`**。
屬性是雙引號包的，而 `JSON.stringify` 產生的字串**也帶雙引號**：

```
onchange="toggleVsnapSel("亞新工程顧問",this.checked)"
                         ↑ HTML 解析器在這裡就把屬性結束掉
```

handler 變成語法錯誤，**按鈕完全沒反應，主控台也不一定看得到錯誤**。

實際發生過：一次壞掉 **9 處**——廠商對比與機關對比的核取方塊、快速加入對手、
更新／移除、刪快照、機關挑選（2 處）、載入失敗重試。而且畫面看起來很正常，
因為**核取方塊視覺上仍會打勾**（那是瀏覽器預設行為，跟 handler 無關）。

**怎麼判斷中招**：看畫面上的計數有沒有跟著動。當時標題寫「目前有 4 份廠商快照。」
卻沒有「，已勾 N 家」，就代表程式眼中一個都沒勾到。

`test/frontend.test.mjs` 有一支**掃原始碼**的測試守著，`test/ui-smoke.mjs` 則用
**真的滑鼠點擊**再守一次（實測把 `jsArg` 換回 `JSON.stringify`，ui-smoke 會失敗）。

相關的第二個坑：**勾選會重繪整個 `<details>`**，若只用 `sel.length>=2` 決定要不要加
`open`，使用者勾第一個時面板會當場收起來。重繪前要先讀目前的展開狀態沿用。

## 2. 公告類型名稱大量共用子字串

隨手 `indexOf` 一定出錯。以台電總公司 `3.13.31` 實測 30,000 筆的分布為證：

| 誤判 | 後果 |
| :--- | :--- |
| `更正決標公告` 含 `決標公告` | 決標數、廠商件數、集中度、落標率**虛增 20.9%**（多 2,709 筆） |
| `無法決標公告` 含 `決標` | 「只看決標公告」多列 **2,937 筆流標案** |
| `撤銷無法決標公告` 含 `無法決標` | 被當成流標，語意相反 |
| `限制性招標(經公開評選…)公告` **不含** `招標公告` | **1,109 筆招標被漏掉** |
| `招標文件公開閱覽公告資料公告` 含 `招標` | 那是招標前置作業，不是招標 |

**規則**：一律走集中的 `isAward` / `isFailedAward` / `isTender` / `isDebarred`，
不要在別處自己寫 `indexOf`。而且「統計」與「顯示」定義不同，刻意分兩組不可互用——
顯示用的 `isAwardNotice` / `isTenderNotice` 含更正（更正公告也是該類別的資訊），
統計用的一案一筆、排除更正與撤銷。

## 3. 欄位名稱也成對出現：`X` 與 `X是否公開` / `X:remind`

決標公告的鍵順序把 `已公告資料:預算金額是否公開`（值是「**是**」）排在
`已公告資料:預算金額` **之前**。用子字串比對的 `pick()` 先撞到「是」，
`parseMoney('是')` = 0。

後果：落標率與「決標／預算比」**永遠算不出來**，而且打開決標公告的標案詳情時
**「採購預算」顯示「是」**。

`總決標金額` 同樣有陷阱：旁邊有 `總決標金額:remind`（中文說明、無數字）與
`投標廠商:投標廠商N:決標金額`（單一廠商金額，不是總額）。

**規則**：金額一律走 `pickMoney()`（鍵尾完全相符、跳過說明類欄位、值須為正數），
決標公告沒有預算時用 `pickMoneyAcross()` 回頭找招標公告。

## 4. localStorage 只有約 5 MB，滿了會讓所有寫入靜默失敗

公告快取是唯一會長到 MB 級的（全國一天約 1,000 則，14 天就可能超過整個配額）。
原本 `persistDayCache()` 的設計是「寫到失敗為止」，也就是刻意填滿配額，
於是其他 30 幾個寫入點全部靜默失敗——**加入追蹤會顯示成功、計數會增加、重載後消失**。
縮小的寫入還會成功，所以症狀是「可以刪不能加」，看起來像隨機 bug。

**規則**：不要直接 `localStorage.setItem`，不要忽略 `LS.set` 的回傳值。
`LS.set` 會先試寫 → 從公告快取回收空間 → 重試 → 還是失敗才明確告知（依鍵節流 30 秒）。
使用者動作寫入失敗時**記憶體要一起回滾**，否則畫面顯示「已追蹤」但重載就不見。

## 5. 分頁會漂移，而 `filename` 不是唯一鍵

抓第 N 頁與第 N+1 頁之間官網若新增公告，位移會讓邊界紀錄被重抓
（台電總公司 30,000 筆裡 34 筆）。

- **`filename` 單獨不唯一**：30,000 筆裡重複 1,026 次，會被多筆共用
- **`job_number + date + type` 也不唯一**：同案同日可有多則（拒絕往來名單一家廠商一則）

**規則**：去重用複合鍵 `filename + job_number + date + type + 廠商名`，
實測與整筆 JSON 比對抓到完全相同的 34 筆，但快 4 倍。

## 6. 連續抓約 15 頁 `listbyunit` 就會被斷線

錯誤是 `TypeError: Failed to fetch`，**不是 HTTP 狀態碼**，所以不要去看 `resp.status`。
原本整個分頁迴圈包在一個 try/catch 裡，第 16 頁一失敗就把前面 15,000 筆全丟掉。

**規則**：每輪上限 15 頁、頁間 700ms、單頁失敗退避重試（1.5s→4s→9s），
失敗也保留已取得的部分並提供續抓。

## 7. 「靜默截斷」比報錯更糟

25 頁上限對 41 頁的機關會直接截掉，而廠商排行、金額合計、發包節奏全部只算那一部分，
畫面上卻完全沒說。

**規則**：不完整就顯示「已取得 X / 官方 Y（第 1–p / t 頁）」、樣本數、涵蓋率警告，
並附續抓按鈕。發包節奏另有獨立警示（公告新到舊排序，未抓完＝缺早年資料）。

## 8. 預測不規律就要說不規律

台電有個案子 2025/08/14 流標、2026/02/04 重招，相隔 174 天。原本按「每曆年取最早一次」
去重，這兩筆分屬不同曆年而雙雙留下，**174 天被當成「半年一次的週期」**，
還跟 5/5 命中的年度案並列同一張表。

**規則**：用「距上一次不到 240 天視為同一輪」收攏，不看曆年；只有間隔接近
365／730／1095 天才標規律，其餘標「不規律」、淡化、排到最後、不計入「120 日內」統計。
**刻意不設「半年」類**——單一個 150~250 天的間隔無法與流標重招區分。

## 9. 測試環境的跨 realm 陷阱

`test/frontend.test.mjs` 用 `node:vm` 跑 HTML 裡抽出來的 `<script>`。
沙箱裡建立的陣列／物件原型屬於沙箱 realm，`assert.deepEqual`（strict 模式即
`deepStrictEqual`）會因原型不符而失敗，**即使值一模一樣**。

**規則**：比較這類回傳值用 `JSON.stringify`。

## 10. `brief.companies.names` 含落標廠商，不是得標名單

**目前為止影響最大的一個誤解。** 名單裡得標與落標混在一起。
2026-09-01 全日 624 則決標公告實測：1,169 個名字裡只有 **725 家真的得標**、
417 家落標，**得標件數虛增 61%**。

一次污染了五個地方：機關洞察的得標廠商排行、市場集中度 CR/HHI、
廠商快照的決標件數與主要機關、拒絕往來名單的得標交叉比對，
以及最明顯的——**「常見共同投標夥伴」把同場競標的對手當成夥伴**。

YJC 是看到「泰興工程顧問的常見共同投標夥伴：吉興工程顧問（19 次）」覺得不對才問的。
查案號 `6331300004`（台中電廠第二期新建燃氣機組，台電核能火力發電工程處）：
`已公告資料:是否共同投標 = 否`，泰興投標落標、吉興投標得標。**是對手，不是夥伴。**

分辨方法在同一份 `brief.companies` 的 `name_key`，**不必多打任何一次 API**：

| `name_key` 欄位 | 意義 |
| :--- | :--- |
| `決標品項:第N品項:得標廠商N:得標廠商` | 得標 |
| `決標品項:第N品項:得標廠商N(共同投標廠商):得標廠商` | 共同投標且得標 |
| `決標品項:第N品項:未得標廠商N:未得標廠商` | 未得標 |
| `投標廠商:投標廠商N:廠商名稱` | 只知道有投標 |
| `標案內容:廠商名稱` | 拒絕往來公告的當事廠商（**沒有得標欄位**） |
| `英文公告:廠商名稱` | 同一家的英文名，**不是另一家公司** |

三個容易再踩一次的細節：

1. **`未得標廠商` 這個字串包含 `得標廠商`。** 先排除「未得標」再比對，
   否則落標會被判成得標——這正是第 2 條那個坑換了個地方重演
2. **多品項的案子同一家可能一項得標、另一項落標**（2026-09-01 實測有），
   規則是**只要有一個純得標欄位就算得標**
3. **拒絕往來公告要用 `recBidders()`**，不能用 `recVendors()`。
   它的廠商掛在 `標案內容:廠商名稱`，沒有任何得標欄位，用得標判斷會回空陣列，
   整份停權名單靜靜消失

**規則**：一律走 `splitCompanies()` →
`recVendors()`（得標，統計用）／`recBidders()`（全部，顯示與拒絕往來用）。
分不出勝負時公告卡片只寫中性的「廠商」，不要假裝知道誰得標。

改這條時**快取結構也要改版**（`pi_daycache2` / `pi_vendor_snap2`），
舊快取沒有勝負資料，留著只會繼續給錯數字。

## 修改流程建議

1. 改完先 `npm test`（43 項，含用真實類型分布驗證決標數、用真實 `name_key` 驗證勝負判讀、
   以及掃原始碼的防護測試）
2. 畫面行為跑 `node test/ui-smoke.mjs`（需自行裝 playwright），它**用真的滑鼠點擊**。
   不要用 `page.evaluate` 直接呼叫函式——**第 1 條那個 bug 就是這樣溜過去的**：
   測到了函式，沒測到渲染出來的屬性。
   mock 也要用**真實形狀**（每頁筆數、混雜的公告類型、`names` 含自己與落標廠商且有英文後綴）
3. 數字類功能要**先手算預期值再比對**，不要看到有數字就當它對
4. 加防護測試時，**要實際把 bug 放回去確認測試會失敗**，不會失敗的測試沒有價值
5. 用 python 做字串替換時，把寫檔放在最後、任何一步比對失敗就 `sys.exit(1)`，
   這樣失敗時檔案完全沒動，不會留下改一半的狀態
6. 要看 API 原始 JSON 不要用 WebFetch——它會摘要截斷，甚至張冠李戴
   （查泰興回了中興的數字）。用瀏覽器在 `https://pcc-api.openfun.app` 這個 origin 直接 `fetch()`
